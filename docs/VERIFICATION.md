## 2. 지리·항로 검증

### 원본 자료
- 강 경계·섬: OSM relation 152336(한강) 구성 way, 밤섬·노들섬 포함. 래스터화 후 4 m 격자 부호거리장(SDF), 기슭 48 m 이내는 원 폴리라인까지의 정확한 거리로 보정
- 지형: AWS Terrain Tiles z14(≈7.6 m/px). SRTM은 지표면 모델이라 여의도·용산의 고층건물이 섞여 있어, 85 m 반경 모폴로지 열림(침식→팽창)으로 건물 크기 돌출을 제거. 남산 정상 고도: 원 DEM 260.1 m(공식 약 262 m)
- 기준 수위: 신곡수중보 관리수위를 반영해 여의도 부근 평수위 ≈ EL 2.5 m를 y=0으로 둠(추정)

### 교량 순서 (서→동, OSM 중심 경도)
서강대교 126.926 → 마포대교 126.936 → **여의도 이랜드크루즈 선착장 126.938** → **원효대교 126.946** → **한강철교 126.952** → **한강대교(노들섬) 126.959** → 동작대교 126.982. 시연 항로는 선착장에서 동쪽으로 원효대교·한강철교를 지나 노들섬 서단 앞에서 회항합니다.

연속 프레임에서 확인한 점과 조치:
- 체적 적운(2026-10-18): 첫 구현은 하늘 패스에서 직접 레이마칭해 GPU 시간이 약 2배가 됨 → 구름 돔 캐시 + 그림자 맵으로 바꿔 같은 페이지 A/B 기준 구름 비용 약 1 ms. 먼 구름의 빗살 무늬(3D 침식 노이즈 파장 < 행진 스텝) → 성긴 탐색 + 정밀 행진, 스텝이 침식을 해상하지 못하면 침식 제거. 사용자 검토 후 구름량을 절반 수준으로 낮춤
- 반해상도 하늘에서 구름 옥타브가 거리별로 끊겨 태양 주변에 동심원 줄무늬 → 원해상도 화소각 사용 + 고층운 저밀도 가장자리 제거로 해결
- 블룸이 태양 주변에 계단 모양 원 → 블룸 입력 밝기 제한
- iWave 격자 시뮬레이션이 발산(커널 고주파 응답 음수) → 해석적 켈빈 항적으로 교체
- 반사 블러가 교각 주변에 회색 번짐 → 반사 블러 LOD 상한
- 입항 직전 3.7 m/s로 접근 → 마지막 150 m 감속(20 m 앞 약 1 m/s)
- 깜빡임: 원거리 창 격자는 상자 필터로 평균화, 그림자 캐스케이드는 텍셀 단위 고정 → 정지·이동 캡처에서 반짝임은 관찰되지 않았으나, 프레임 간 수치 비교는 하지 않음(**정량 미검증**)

## 7. 성능

### 실사용 지속 (`tools/sustain.mjs`, 1920×1080 창, 자동 화질, vsync)
3분 동안 15초 간격 12회 측정 모두 **60.1 fps**, 17.5 ms 초과 프레임 **0%**, 25 ms 초과 0건, 렌더 해상도 1920×1080 유지(동적 해상도 미작동), GPU 시간 11.3–13.9 ms.
측정 구간은 출항~원효대교 접근(s = 20→520 m)입니다.

### 9.3 모바일 성능

**먼저 측정(이전 빌드, `?mobile=1`, 1578×887):** 패스별 GPU 시간은 메인 패스가 75–85%(golden_city 22 ms 중 메인 22.3 ms, 컴퓨트 2.2, 반사 1.0, 그림자 0.5, 하늘 0.5, 블룸·합성 0.5). 메인 패스 내용별(그룹 생략 비교): 수면 7–8 ms, 건물·교량·배 5–7 ms, 지형 약 6 ms, 하늘 합성 2–3 ms, 나무 0. 그래서 반사·그림자 해상도는 효과가 작고, 메인 패스의 셰이딩·정점·과다 그리기를 줄이는 쪽을 택했습니다.

| 조치 | 대상 | 효과(쌍 비교) |
|---|---|---|
| 배를 먼저, 건물 타일을 가까운 순으로 그림(조기 깊이 판정으로 가려진 파사드 셰이딩 생략) + 수면 0.8 m 아래 강바닥 셰이딩 생략(불투명 물에 덮임) | 모든 기기, 화면 동일(픽셀 차 0) | 데스크톱 −5…−17% |

검토했지만 기본값으로 쓰지 않은 것: **4× MSAA 끄기**는 이 기기에서 1.4 MP 프레임의 약 20%(메인 패스 4–6 ms)를 줄이지만 난간·와이어·건물 윤곽이 계단처럼 보여 기본값은 유지하고 `?msaa=1`로만 남김. 실제 휴대폰의 타일 GPU(Vulkan)는 MSAA 해소가 칩 안에서 끝나 비용이 더 작을 수 있으나 **미측정**. 구름 돔 갱신(약 0.4–0.9 ms)은 측정 편차보다 작아 두었습니다.

동적 해상도: 이 기기는 1.4 MP에서 GPU 시간이 20 ms를 넘는 장면이 많아, 대부분의 장면에서 이전·이후 모두 하한(0.60배, 947×532)에 머뭅니다. 그래서 '동적 해상도에서 GPU' 열(같은 해상도라면 GPU 시간 차이가 곧 여유)과 하한보다 위에 머문 장면의 배율 변화를 같이 보아야 합니다.

#### 결과 요약

- 모바일 모드(1.4 MP): **33개 고정 장면 모두 GPU 시간 감소**(−1.7 … −24.4%, 중앙값 약 −17%). 늘어난 유람선·노들섬 비용을 포함한 값입니다.
- 동적 해상도(`--dyn`: 1920×1080 창 → 1.4 MP 예산 → 자동 화질, 2라운드): 어느 장면도 배율이 낮아지지 않았고 6개 장면에서 올라감(`near_hull` 0.65→1.00, `bridge_under` 0.94→1.00, `nodeul_complex_night` 0.60→0.75 등). 나머지는 이 기기에서 이전·이후 모두 하한 0.60에 머물러, 같은 해상도에서의 GPU 시간이 줄어든 것으로 나타남.
- 데스크톱(1080p): 가장 큰 증가 `boat_aftdeck` **+4.9%**(5% 이내), `bridge_under` +1.4%, `boat_foredeck` +0.6%, 나머지 30개 장면은 감소(−0.8 … −19.8%).
- 로딩: 시작 버튼까지 이전 2.58–2.81 s → 이후 2.52–2.61 s(메쉬 생성 434–528 → 418–451 ms, 노들섬·유람선 생성 포함). 데이터 파일은 변경 없음(약 12 MB).
- 지속 실행: 이전 39–43 fps → 이후 45–51 fps(둘 다 해상도 하한 947×532). 이 측정만은 이전→이후 순서로 연달아 돌려 쌍 비교가 아니므로 열 상태 차이가 섞일 수 있습니다.
- 모든 측정에서 콘솔·WebGPU 검증 오류 0건.
